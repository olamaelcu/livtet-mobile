# Agent Guidelines for `mobile/android/`

This file governs AI agent behaviour inside the Livtet Android app. Read it
together with the root [AGENTS.md](../../AGENTS.md) and the
[mobile/android/README.md](README.md). The README documents the app surface;
this file captures the rules an agent must follow.

The Android app is a **separate product** that shares the Livtet brand name. It
is not a Tauri target, not a "mobile build of Tauri", and Tauri configuration
(`.browserslistrc`, `tauri.conf.json`, `packages/livtet-tauri-web/`) is
irrelevant to it.

## Required Skills

- `guardrails` — never restart, start, or kill the Android build pipeline,
  emulator, or app. Always ask before running `mise run android-*`, `gradle`, or
  `adb install`. Clean stale native libs
  (`rm -rf mobile/android/app/src/main/jniLibs`) before any build.
- `mise-tools` — required when a `mise.toml`-declared binary returns
  `command not found` (for example `uniffi-bindgen` or the Android SDK tools).

## Commands

The Android toolchain is set up by `mise run android-dev-init`, which runs
automatically after `android-sdk` install/update. From there:

```bash
mise run android-build          # native build + UniFFI bindings + APK
mise run android-install        # install APK on target (verifies ABI)
mise run android-test           # unit + instrumented tests
mise run android-lint           # ktlint, detekt, Android lint
                                #   (--fix auto-fixes via ktfmtFormat +
                                #    ktlintFormat + detekt --auto-correct)
mise run android-clean          # wipe Gradle caches + build/ + jniLibs
mise run android-emulator       # create / launch the phone or tablet AVD
```

The dev loop aliases `aw` (android-watch), `aii` (android-install-incremental),
and `apk` (android-run-emulator) are available once the toolchain is installed.

### Native Library Hygiene

`app/src/main/jniLibs/` caches prebuilt `.so` files across builds. Before any
build that touches `core/livtet-ffi/`, delete the directory:

```bash
rm -rf mobile/android/app/src/main/jniLibs
mise run android-build
```

Leaving stale libs in place produces confusing "Library not found" or ABI
mismatch errors.

## UniFFI Bindings

The Kotlin bindings at `mobile/android/build/generated/source/uniffi/kotlin/`
are generated by `uniffi-bindgen` during `mise run android-build`. The `:app`
module adds the directory as an extra `srcDir`:

```kotlin
sourceSets["main"]
    .kotlin
    .srcDir(layout.buildDirectory.dir("../../build/generated/source/uniffi/kotlin"))
```

Treat these files as build artifacts: do not hand-edit, and re-run the Android
build after every change to `core/livtet-ffi/` or `core/livtet-types/`
(`livtet-ffi` re-exports types from `livtet-types`).

## Product Flavors

Three flavors share the `store` dimension:

- `playstore` — default Google-aligned build. Sentry DSN injected from
  `LIVTET_SENTRY_DSN_MOBILE`. Telemetry opt-in by build configuration.
- `fdroid` — F-Droid-aligned build. Empty Sentry DSN (no tracking).
- `generic` — sideload build. Empty Sentry DSN (no tracking).

Sentry never initialises in `fdroid` and `generic` because
`BuildConfig.SENTRY_DSN` is empty by design; there is no runtime consent dialog.
(There is no `baseline-prof.txt` checked in, and no `:benchmarks`
macrobenchmark module — the baseline-profile tooling is set up in
`gradle/libs.versions.toml` and `build-logic/` but not yet wired into the
Gradle build, so baseline-profile regeneration is not yet actionable.)

## Release Signing and Sentry Uploads

- **Signing config** lives in `app/build.gradle.kts` for the `playstore` flavor
  only. Set `LIVTET_STORE_FILE`, `LIVTET_STORE_PASSWORD`, `LIVTET_KEY_ALIAS`,
  and `LIVTET_KEY_PASSWORD` (env vars or `~/.gradle/gradle.properties`).
  `fdroid` and `generic` are signed by external build servers, never by the
  local Gradle build.
- **Sentry** — only the runtime Android SDK is wired in (`io.sentry:sentry-android`
  as an `implementation` dependency). The `io.sentry.android.gradle` plugin is
  declared in `gradle/libs.versions.toml` but is **not** applied to `:app`, so
  no ProGuard-mapping / native-debug-symbols / source-context uploads happen
  from the Gradle build. `SentryAndroid.init(...)` in `LivtetApp.onCreate()`
  is the only initialisation path; it runs only when `BuildConfig.SENTRY_DSN`
  is non-empty (the `playstore` flavor). If/when the Gradle plugin gets
  applied, the expected env vars are `SENTRY_ORG`, `SENTRY_PROJECT`, and
  `SENTRY_AUTH_TOKEN` (with `project:releases` scope).

## Generated Files and Artifacts

- `app/src/main/jniLibs/` — prebuilt `.so` files; safe to delete at any time.
  `mise run android-build` repopulates them from `core/target/<abi>/...`.
- `build/generated/source/uniffi/kotlin/` — UniFFI Kotlin bindings. Do not
  hand-edit.
- `core/designsystem/src/main/res/drawable/lucide_*.xml` — Lucide icon vector
  drawables (committed; generated by the design-tokens build in the
  `livtet-branding` sibling repo). Do not hand-edit.
- `core/designsystem/src/main/kotlin/.../LucideIcons.kt` — companion
  `R.drawable.lucide_*` constants. Do not hand-edit.

## Generated Design Tokens

The Compose color schemes, brand typography, launcher icons, and per-flavor
mipmaps are produced by the design-tokens build in the **sibling**
`livtet-branding` repo at <https://github.com/olamaelcu/livtet-branding>
(consumed via the `includeBuild`
substitution in `mobile/android/settings.gradle.kts` as
`net.olamaelcu:livtet-branding`). There is no `mise run design-tokens` task in
this repo — regenerate from the branding repo:

```bash
# from a local clone of <https://github.com/olamaelcu/livtet-branding>
tsx generate.ts --platform android    # writes into android/library/src/
```

Do **not** hand-edit anything under `android/library/src/` in
<https://github.com/olamaelcu/livtet-branding>
once generated. The committed files to watch in this mobile repo are
`mobile/android/core/designsystem/src/main/kotlin/.../LucideIcons.kt` and
`mobile/android/core/designsystem/src/main/kotlin/.../LivtetRadius.kt`; both
have GENERATED-file headers.

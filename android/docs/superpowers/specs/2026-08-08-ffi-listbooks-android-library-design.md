# FFI `listBooks` + Android Library List — Design Spec

**Date**: 2026-08-08
**Status**: Approved
**Scope**: Expose `list_books` from the Rust FFI core and rewire `LibraryScreen.kt`
to render a paginated book list.

## 1. Summary

Add a `list_books(limit, offset, order)` FFI export to `core/livtet-ffi/` plus
the two UniFFI types it depends on (`Book`, `BookSearchSortOrder`). Wire it
through `mobile/android/.../Bridge.kt` and replace the placeholder body of
`mobile/android/.../LibraryScreen.kt` with a `LazyColumn` that renders the
returned rows. This unblocks the rest of the Library surface (search, filters,
pull-to-refresh, cover thumbnails) as separate follow-up commits.

## 2. FFI Rust side (`core/livtet-ffi/`)

### 2.1 New file `src/books.rs`

Holds the `Book` record, the `BookSearchSortOrder` enum, and the `list_books`
export. Pattern after the existing `lookup.rs` / `init.rs` modules (each
domain lives in its own file and is wired into `lib.rs` via `mod books;`).

#### `Book` record

```rust
#[derive(uniffi::Record)]
pub struct Book {
    pub id: DbId,
    pub title: String,
    pub description: Option<String>,
}
```

`DbId` is already registered as a UniFFI custom type at `lib.rs:17-26`, so no
extra FFI wiring is required. The shape is intentionally narrow — every field
the iOS-side `Book` consumers actually read today (`book.id`, `book.title`,
`book.description` in `NewPuzzleSheet.swift:27-37`).

#### `BookSearchSortOrder` enum

```rust
#[derive(Debug, Copy, Clone, uniffi::Enum)]
pub enum BookSearchSortOrder {
    /// Sort by `works.created_at` ASC (oldest first).
    Ascending,
    /// Sort by `works.created_at` DESC (newest first).
    Descending,
}
```

The iOS bridge already uses `.ascending` / `.descending` in
`LivtetCoreBridge.swift:139,264` and `LibraryView.swift:309-310`, so the
serialised names are pinned by uniffi to those spellings.

#### `list_books` export

```rust
#[tracing::instrument(name = "ffi_list_books", skip_all, err)]
#[uniffi::export]
pub async fn list_books(
    limit: i32,
    offset: i32,
    order: BookSearchSortOrder,
) -> Result<Vec<Book>, MobileError>
```

Implementation sketch:

```rust
let state = get_state()?;                                // existing helper at lib.rs:271
let db = state.db_conn();                                // sea_orm::DatabaseConnection
let limit = limit.max(0) as u64;
let offset = offset.max(0) as u64;

let mut q = works::Entity::find();
q = match order {
    BookSearchSortOrder::Ascending  => q.order_by_asc(works::Column::CreatedAt),
    BookSearchSortOrder::Descending => q.order_by_desc(works::Column::CreatedAt),
};

let rows = q
    .offset(offset)
    .limit(limit)
    .all(db)
    .await?;                                             // From<DbErr> for MobileError already wired

Ok(rows.into_iter().map(|m| Book {
    id: m.id,
    title: m.title,
    description: m.description,
}).collect())
```

`limit` / `offset` are clamped to `>= 0` to harden against a hostile caller.
The query is wrapped in `runtime::block_on` is **not** needed — the function
itself is `async`, matching the existing pattern of `search_providers`,
`init_plugins`, and `seed_database`.

The error path uses the existing `impl From<livtet_database::orm::DbErr> for MobileError`
at `lib.rs:251-255`.

### 2.2 Wire into `lib.rs`

Add `mod books;` next to the other module declarations. The `Book` record and
`BookSearchSortOrder` enum are referenced directly through the uniffi-generated
Kotlin / Swift bindings, so neither needs an explicit re-export.

## 3. Android side (`mobile/android/app/src/main/java/net/olamaelcu/livtet/`)

### 3.1 `Bridge.kt` — new wrapper

Add next to the existing wrappers at `Bridge.kt:60-67`:

```kotlin
suspend fun listBooks(
    limit: Int = 50,
    offset: Int = 0,
    order: BookSearchSortOrder = BookSearchSortOrder.Descending,
): List<Book> =
    withContext(Dispatchers.IO) {
        net.olamaelcu.livtet.ffi.listBooks(
            limit = limit.toInt(),
            offset = offset.toInt(),
            order = order,
        )
    }
```

The default `limit = 50` matches the Android README's "Paginated book list
(50 per page, newest first)" contract. `Book` and `BookSearchSortOrder` are
generated by `uniffi-bindgen` into
`mobile/android/build/generated/source/uniffi/kotlin/`, so they're already
importable from `net.olamaelcu.livtet.ffi.*`.

### 3.2 `LibraryScreen.kt` — render the list

Replace the empty-state placeholder with a `LazyColumn` driven by a
`ViewModel`:

- `LibraryViewModel` (new file `LibraryViewModel.kt` in the same package)
  owns `books: List<Book>`, `isLoading: Boolean`, `error: AppError?`.
- `load()` calls `Bridge.listBooks(limit = 50, offset = 0, order = DESCENDING)`.
- The composable renders one row per `Book` with the title (Material 3
  `titleMedium`) and the description (`bodySmall`, omitted when null).
- While `isLoading`, show a centred `CircularProgressIndicator`.
- On error, show a `Snackbar` (or an inline `Card` with a retry button —
  whichever fits the existing Dashboard error pattern; will match that
  during implementation).
- Empty state shows `getEmptyStateQuotation()` text — already plumbed
  through `Bridge.kt:55-56`.

Hard "not in this change" list:
- No filter chips (no `getDistinctFormats` / `getDistinctLanguages` /
  `getDistinctWorkStatuses` calls).
- No search box.
- No pull-to-refresh.
- No `+` button opening the Add Book wizard.
- No cover images.
- No pagination / scroll-to-load-more. The 50-row page is loaded once
  per screen entry; the user navigates away and back to refresh.

## 4. Tests

### 4.1 Rust (`livtet-ffi/src/books.rs`)

`#[cfg(test)] mod tests` block running in-process:

1. `list_books_returns_seeded_works_in_descending_order` — call
   `livtet_core::seed::seed_database(&conn, &SeedConfig { num_works: 5, .. })`,
   then `list_books(limit=5, offset=0, order=Descending)`, assert the
   returned `Book.id` values match the inserted `works.id`s in reverse
   `created_at` order.
2. `list_books_respects_limit_and_offset` — seed 5 works, call
   `list_books(limit=2, offset=1, order=Ascending)`, assert exactly 2 rows
   back, starting at the second-oldest.
3. `list_books_clamps_negative_limit_and_offset` — call
   `list_books(limit=-5, offset=-3, order=Descending)` against an empty
   pool; assert it returns `Ok(vec![])` instead of erroring on the SQL
   layer.
4. `book_carries_title_description` — seed one work with both fields
   set, assert the returned `Book.title` / `Book.description` match.

Tests use `livtet_core::SharedState::connect("sqlite::memory:")` and
`init_state(...)` to satisfy `get_state()`'s `OnceLock` requirement; a
`#[ctor`-style `OnceLock::set_or_init`-with-error pattern isn't available,
so each test that needs state will guard on `is_initialized()` first.

### 4.2 Android

No instrumented test in this change. The existing
`mobile/android/app/src/androidTest/java/.../AddBookSearchTest.kt` covers
the wizard search surface; the library list is plain Compose and will get
a snapshot test in a follow-up alongside the cover-image work.

## 5. Out of scope (each is its own follow-up commit)

- `createBook`, `getBook`, `getEditionsWithCoversForWork`, `findOrCreateAuthor`,
  `linkWorkAuthor`, `linkWorkTag`, `linkWorkGenre`, `linkWorkSubject`,
  `createEdition`, `createEditionForWork`, `mergeReplaceWork`,
  `linkIsbnToExistingEdition`, `findWorkByIsbn`, `findWorksByTitlePrefix`.
- `listBooksWithFilters`, `BookListFilters`, the three distinct-* filters,
  and `getEmptyStateQuotation`'s caller (already wired in `Bridge.kt` but
  unused).
- `RecentlyReadBook` / `DashboardStats` / `RecentSearch` — the
  `DashboardScreen` currently uses stub data; bringing those FFI exports
  up is its own change.
- Cover thumbnails in `LibraryScreen`.
- Search, pull-to-refresh, pagination, filter chips.
- iOS-side work — the Swift bindings will regenerate cleanly once the
  Rust side compiles, but no iOS call sites need to change for this
  Android-focused change.
